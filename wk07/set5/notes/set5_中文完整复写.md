## 模块 1：从单周期实现回顾到问题暴露
- 单周期微体系结构中，每条指令都在一个 machine clock cycle 内完成。
- 指令处理通常可以分成取指、译码/读寄存器、执行/地址计算、访存、写回等阶段。
- 在单周期设计里，这些阶段都被压进同一个时钟周期中完成，因此从 ISA 角度看，系统只发生一次从 AS（architectural state）到 AS' 的转换。
- 单周期设计不引入对程序员可见的中间状态；执行过程中的变化都要在一个周期末统一提交。

## 模块 2：单周期微体系结构为什么不理想
- 时钟周期必须被最慢指令决定，即使很多简单指令根本不需要这么久。
- 现实中的内存访问很慢，因此像寄存器加法、跳转这类简单操作，也会被最慢的访存路径拖慢。
- 如果一条指令在不同阶段要多次用到同一类资源，单周期设计往往不得不为最坏情况准备并行硬件，硬件成本高。
- 这种设计不利于优化常见情况，因为系统总是被迫围绕最坏情况定时。

## 模块 3：多周期设计的核心思想
- 将“instruction processing cycle”和“machine clock cycle”分离开。
- 一条指令不再必须在一个时钟周期内完成，而是被拆成多个状态（states），每个状态占用一个时钟周期。
- 不同指令可以走不同的状态路径，因此简单指令用更少周期，复杂指令用更多周期。
- 从 ISA 视角，仍然只关心给定指令和 AS 之后最终得到的 AS'；中间多出来的状态属于微体系结构内部的、programmer-invisible state。

## 模块 4：多周期设计的收益与代价
- 收益：
  - 时钟周期可以独立于“最慢指令总延迟”来确定，关键路径更短。
  - 可以优化常见指令，让它们只走必要的状态数。
  - 可以复用同一份硬件资源，不必为了同一条指令的不同阶段复制资源。
- 代价：
  - 需要额外的微体系结构寄存器来保存中间结果。
  - 每个时钟边界都会支付寄存器建立/保持等 sequencing overhead。
  - CPI 不再固定为 1，而是随指令类型变化。

## 模块 5：Datapath 与控制逻辑在多周期中的角色
- Datapath 负责真正搬运和处理数据，包括 ALU、寄存器文件、mux、存储器连接和各种中间寄存器。
- Control logic 负责在每个状态下发出控制信号，决定 datapath 当周期该做什么，以及下一周期进入哪个状态。
- 多周期实现本质上可以看成一个有限状态机（FSM）：当前状态决定本周期的控制信号，也帮助决定下一状态。

## 模块 6：多周期 ARM Datapath 的总体结构
- 与单周期实现相比，多周期 ARM 处理器强调“只用一个 memory、只用一个 ALU/adder”，以降低硬件成本。
- 为了复用这些共享资源，需要加入单周期中不需要的非架构寄存器，保存取回的指令、读出的操作数、ALU 结果、访存结果等中间值。
- 这些寄存器不是程序员可见的 architectural state，而是微体系结构为了分阶段执行指令而引入的内部状态。

## 模块 7：LDR 指令如何在多周期中执行
- 以 `LDR R0, [R1, #32]` 为例，需要完成：
  - 从内存取出指令。
  - 从寄存器文件读出基址寄存器 `R1`。
  - 用 ALU 计算有效地址 `R1 + #32`。
  - 访问该地址，读出数据。
  - 将数据写回目标寄存器 `R0`。
- 课件在构造 datapath 时把这个过程拆成了更细的演示步骤，包括取指、读寄存器、算地址、读内存、写回，以及单独展示的 PC 更新。
- 在最终的控制器 FSM 里，PC 更新与取指被合并进 Fetch 状态，因此最终统计时 `LDR` 按 5 个周期计算，而不是 6 个独立状态。

## 模块 8：PC 与 R15 的特殊处理
- ARM 中 PC 可以像普通寄存器一样被读写，但语义不是“直接读当前 PC 寄存器值”那么简单。
- 当 R15 被作为源寄存器读取时，寄存器文件需要提供 `PC + 8`。
- 课件中的解释是：
  - 第 1 步取指后，PC 已经更新到 `PC + 4`。
  - 第 2 步再用 ALU 计算 `(PC + 4) + 4 = PC + 8`，并把这个值送到寄存器文件的 R15 输入路径。
- 当指令结果要写回 PC（例如目的寄存器就是 R15，或执行分支），则通过已有的数据通路把结果送回 PC，并断言 `PCWrite`。

## 模块 9：STR、数据处理指令与分支指令
- `STR` 的关键是把寄存器中的数据写到由基址加偏移算出的地址中。
- 数据处理指令（DP）分为立即数版本和寄存器版本：
  - 立即数版本不需要额外 datapath 改动。
  - 寄存器版本需要从寄存器文件中读取 `Rn` 和 `Rm` 作为 ALU 输入。
- 分支指令 `B` 需要计算分支目标地址：
  - `BTA = ExtImm + (PC + 8)`
  - 其中 `ExtImm = sign-extend(imm24 << 2)`。
- 在最终 FSM 中，典型周期数为：
  - `B`：3 cycles
  - `DP`：4 cycles
  - `STR`：4 cycles
  - `LDR`：5 cycles

## 模块 10：多周期控制器与指令译码
- 控制器先做指令译码，再通过主 FSM 驱动各个执行状态。
- 课件给出了一个简化的译码关系：
  - `RegSrc0 = (Op == 10_2)`
  - `RegSrc1 = (Op == 01_2)`
  - `ImmSrc[1:0] = Op`
- 对应到常见指令类：
  - `LDR/STR` 使用 `Op = 01`
  - `DP immediate / DP register` 使用 `Op = 00`
  - `B` 使用 `Op = 10`
- 主控制器是一个 FSM，常见状态包括 Fetch、Decode、MemAdr、MemRead、MemWB、MemWrite、ExecuteR、ExecuteI、ALUWB、Branch 等。
- 指令执行的本质，就是控制器按照指令类别在这些状态之间切换。

## 模块 11：多周期处理器的性能分析
- 多周期处理器有两个独立可调的维度：
  - 时钟周期时间（clock cycle time）
  - 每条指令平均需要的周期数（average CPI）
- 与单周期相比：
  - 单周期：`CPI = 1`，但时钟周期长。
  - 多周期：时钟周期短，但不同指令 CPI 不同。
- 课件给出的例子中：
  - `B = 3 cycles`
  - `DP, STR = 4 cycles`
  - `LDR = 5 cycles`
- 若指令混合为 25% loads、10% stores、13% branches、52% R-type，则平均 CPI 为：
  - `Average CPI = (0.13)(3) + (0.52 + 0.10)(4) + (0.25)(5) = 4.12`
- 关键路径分析在课件中给出：
  - 假设寄存器文件比内存快，且写内存比读内存快，
  - 则多周期时钟周期可写成 `Tc2 = tpcq + 2tmux + max(tALU + tmux, tmem) + tsetup`
- 用课件中的参数代入后得到：
  - `Tc2 = 340 ps`
- 执行时间仍满足总公式：
  - `Execution Time = (# instructions) × CPI × clock period`
- 课件例子中，1000 亿条指令、`CPI = 4.12`、`Tc = 340 ps`，得到执行时间约为 140 秒。

## 模块 12：为什么多周期控制自然引出 microprogramming
- 多周期实现本来就已经把“执行一条指令”拆成多个状态，这为 microprogramming 提供了很自然的抽象层。
- 硬连线控制（hardwired control）是直接把指令字段接入控制逻辑，由组合/时序电路产生控制信号。
- 微程序控制（microprogrammed control）则把每个状态下的控制信号写成“微指令（microinstruction）”，存放在控制存储器（control store）中。
- 一条机器指令的执行，可以看成一串微指令驱动下的数据通路操作序列。

## 模块 13：Microprogramming 的关键术语
- `Microinstruction`：当前状态对应的一组控制信号。
- `Microsequencing`：决定从当前状态跳到下一个状态，以及取出下一条微指令的过程。
- `Control store`：保存全部微指令的特殊存储结构。
- `Microsequencer`：根据当前状态和部分指令信息，决定下一条微指令地址的部件。
- 每个 FSM 状态可以对应 control store 中唯一的一条微指令。
- 在一个时钟周期里，datapath 和 microsequencer 是并行工作的：一边完成本周期的数据处理，一边决定下一周期该取哪条微指令。

## 模块 14：Microprogrammed Control 的价值
- 通过微代码，可以让一个相对简单的数据通路完成更复杂的 ISA 语义。
- 微指令序列可以被看作一种“对程序员不可见的内部 ISA（u-ISA）”。
- 如果 datapath 已经具备基础操作能力，那么加入新指令、扩展复杂语义，很多时候只需要修改微代码，而不一定要重做整套硬件。
- 微代码还可以用于修补已出厂处理器中的某些硬件实现缺陷，因此现实系统中常见微代码补丁。

## 模块 15：多周期的局限与为什么进一步走向流水线
- 多周期虽然比单周期更节省资源，但不同阶段之间缺乏并发性。
- 当一条指令在某个阶段使用部分资源时，其他大量硬件可能处于空闲状态。
- 例如：
  - 一条指令在译码时，取指硬件可能闲着。
  - 一条指令在访存时，很多 datapath 部分都闲着。
- 这说明系统还有提高并发度的空间。

## 模块 16：流水线的基本动机
- 目标是提高 instruction throughput，也就是单位时间完成更多指令。
- 核心想法是：让不同指令同时处于不同的处理阶段，像装配线一样重叠执行。
- 经典阶段仍然是 IF、ID/RF、EX、MEM、WB，只不过这些阶段开始由不同指令并行占用。
- 好处是吞吐率提升，常用的直观说法是“让 1/CPI 变大”。
- 代价是控制更复杂，必须开始认真处理数据冒险、控制冒险和资源冲突等问题；这也是后续内容的重点。
